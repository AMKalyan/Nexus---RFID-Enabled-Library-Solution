## Safeguards observed

- A full backup (`nexus-1.0.0-20261007T144402Z-pre-migration-….dump`, 3.3 MB, with a `.sha256` file) was taken before anything was written.
- Legacy-schema fingerprints were taken before and after the insert, and matched. The commit would have been aborted otherwise.
- All 19,200 rows were inserted in one transaction, each tagged with the batch id, which makes batch rollback exact.
- Staging, validation and commit are each recorded in the audit log.

## Performance note

The first implementation used ORM bulk statements. It issued one round trip per few rows, and staging 2,000 rows took 21 s on the development host. Moving to core multi-row inserts and pipelined updates brought that to 2.8 s, and the full 20,000 rows to the 13.7 s above.

## Batch rollback rehearsal
